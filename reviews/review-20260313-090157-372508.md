## Critical

### 1. Direct imports now fail because `utils.llm` creates a package cycle
- File: `utils/llm.py`
- Line: `16`
- Severity: `critical`
- Category: `Diff`
- Description: `utils.llm` now imports `noa.runtime` at module import time. Importing `noa.runtime` first executes `noa/__init__.py`, which re-exports `auto_adapt`, and `noa.auto_adapter` imports `utils.llm` again. That leaves `utils.llm` partially initialized and breaks direct imports such as `import utils.llm` and `import target_systems.pubmedqa.config` before any runtime logic starts.
- Suggested fix: Remove the top-level dependency from `utils.llm` to `noa.*`. Move the runtime helpers behind a lower-level module that does not import `noa/__init__`, or make those imports function-local so importing `utils.llm` does not recurse back through `noa.auto_adapter`.

## High

### 2. Rejected validation candidates still poison the accepted snapshot baseline
- File: `noa/unified_agent.py`
- Line: `1462`
- Severity: `high`
- Category: `Diff`
- Description: `_commit_best_before_observe()` snapshots `pre_val_eval`, then calls `self.sandbox.accept_candidate(best_label)` before running validation. `accept_candidate()` refreshes the sandbox's `accepted` snapshot. If validation later rejects the candidate, the code restores only `source_dir` via `restore("pre_val_eval")`; it does not restore the accepted snapshot. Because future checkpoints fork from `SandboxManager._get_checkpoint_base()`, subsequent candidates can be based on a rejected tree instead of the restored baseline.
- Suggested fix: Evaluate the candidate without calling `accept_candidate()` first, or explicitly restore/reset the accepted snapshot when validation rejects the candidate.

### 3. `max_llm_calls` is still configurable and reported, but it is no longer enforced
- File: `noa/core/protocol.py`
- Line: `461`
- Severity: `high`
- Category: `Diff`
- Description: `OptimizationBudget.reached_limit()` now stops only on `max_steps` and `max_evals`. `llm_calls_used` is still tracked, `max_llm_calls` is still accepted by the orchestrator and scripts, and summaries still report it as if it matters. That silently removes a resource-safety guard while leaving the API contract intact.
- Suggested fix: Restore the `llm_calls_used >= max_llm_calls` check in `reached_limit()`, or remove `max_llm_calls` from configs, constructors, and summaries if the limit is intentionally retired.

## Medium

### 4. Candidate merging still cannot carry file deletions forward
- File: `noa/sandbox_manager.py`
- Line: `290`
- Severity: `medium`
- Category: `Diff`
- Description: `merge_candidates()` only walks files that still exist in each candidate directory. A candidate that deletes a file leaves nothing to walk, so the deletion is invisible to the merge step and the merged candidate keeps the baseline copy. That can resurrect files a source candidate intentionally removed.
- Suggested fix: Compare each candidate's file set with the checkpoint base and propagate deleted paths into the merged candidate alongside modified files.

### 5. The new PubMedQA split logic depends on object identity instead of the dataset's stable IDs
- File: `scripts/run_pubmedqa.py`
- Line: `105`
- Severity: `medium`
- Category: `Diff`
- Description: The train/validation/test split excludes records via `id(x)`. That works only while the exact same Python objects stay alive in memory. The dataset objects already carry stable IDs, so this split becomes fragile under refactors, serialization, caching, or any re-materialization of samples, and can leak evaluation examples back into the training pool.
- Suggested fix: Build the exclusion sets from the dataset's stable example IDs instead of `id(x)`.

### 6. The dashboard reports a different Together RPM limit than the runtime actually enforces
- File: `dashboard/data.py`
- Line: `15`
- Severity: `medium`
- Category: `Holistic`
- Description: `dashboard/data.py` hardcodes `DEFAULT_RPM_BY_PROVIDER["together"] = 55`, while `utils/llm.py` uses `3000` as the Together default. When a run record omits `llm_rpm_limit`, the dashboard displays the wrong configured limit. `tests/test_dashboard_data.py` currently locks in the incorrect `55` value, so the mismatch is now codified rather than detected.
- Suggested fix: Centralize provider inference and default RPMs in one shared module and have both the runtime and dashboard read from it. Update the dashboard test to assert the shared source of truth.

### 7. The changed high-risk control paths shipped without targeted regression coverage
- File: `tests/`
- Line: `n/a`
- Severity: `medium`
- Category: `Diff`
- Description: The new dashboard path has tests, but the riskier behavior changes do not: there is no regression test for the broken direct-import path, no test for the rejected-validation rollback keeping the accepted snapshot clean, no test for `OptimizationBudget.reached_limit()` enforcing `max_llm_calls`, and no merge test covering deletion propagation. ### 8. Runtime configuration is still effectively undocumented

- Line: `1`
